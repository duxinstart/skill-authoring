目录取舍与设计流程

除了 SKILL.md，其余全部可选。按需增加，不要预先堆。目录不是"设计出来"的，是"长出来的"。

1. 什么时候需要哪个目录

目录 / 文件必需性什么时候才需要它
SKILL.md必需永远需要。没有它就不是一个技能。
references/可选当 SKILL.md 装不下、或存在"只有特定情况才用得上"的详细知识（领域规则、API 细节、错误表）时。
scripts/可选当存在确定性、可重复、agent 每次都要重新实现的操作时（解析格式、生成图表、校验产物）。
assets/可选当需要固定的输出模板、数据结构定义，或静态查找表时。
evals/可选当技能需要长期维护、验证质量，或要与"没有技能时"对比效果时。
README.md
LICENSE
CHANGELOG.md		给人看当技能要对外发布 / 团队共享 / 版本化管理时。它们不进模型上下文。
一句话原则：当某类内容多到撑不住 SKILL.md，或某段逻辑反复被重写，就把它拆出去。

2. 六步演进路径

不要一开始就规划完整目录树。从最小可用开始，用真实任务驱动拆分。

只写 SKILL.md

从最小形态起步：frontmatter + 何时使用 + 核心流程。能跑通一个真实任务就够了。

在真实任务中试用

拿真实提示词跑几遍，观察 agent 的表现与执行轨迹，记录它做错、绕路、重复的地方。

内容变长 → 拆出 references/

当 SKILL.md 里的"详细知识"越积越多，把它移出去，并在 SKILL.md 留一张路由表指明何时加载。

逻辑重复 → 加 scripts/

若发现 agent 每次都重写同一段逻辑（建图表、解析格式、校验输出），就把它写成经过测试的脚本。

格式要固定 → 加 assets/

需要稳定的输出结构或静态数据时，加 templates / schemas / data。

要长期维护 → 加 evals/

用测试用例 + 断言锁定质量，之后每次改动都跑一遍，确保不回退。

3. 设计时的三个判断问题

  • 这块内容"每次都要用"还是"偶尔才用"？
    每次都用 → 留在 SKILL.md；偶尔才用 → 拆出去 + 在路由表里给触发条件。
  • 这段操作"每次都要重做"吗？
    是 → 写成脚本，别再让模型现写。
  • 删掉这个文件，agent 会做错吗？
    不会 → 它可能根本不需要存在。警惕过度设计。

4. 常见反模式

  • 一开始就铺满完整目录树 → 大部分目录会空着，纯属负担。
  • 为"以后可能用到"而预留目录 → 用不到就是噪音。
  • SKILL.md 与 references/ 内容重复 → 浪费上下文，还容易不同步。
  • 资源文件没有触发条件 → 永远不会被加载，等于不存在。
  • 把主流程也拆进 references/ → 主干必须留在 SKILL.md，拆走的只能是细节。
