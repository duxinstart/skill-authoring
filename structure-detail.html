Structure

目录结构详解

每个文件「装什么、何时被读、为何单独拆出来」。判断标准只有一条：agent 需要它时，能否凭 SKILL.md 里的触发条件准确找到并按需加载？

本页是总览：说明每个目录的职责与边界；具体怎么写，见各专项页。标 必需 的是技能运行所必需，其余为可选。

SKILL.md必需

整个技能的唯一入口。它不做具体工作，只负责两件事：告诉 agent「这个技能是什么、什么时候用」，以及「遇到不同情况该去读哪个文件」——这就是「路由表」的含义。撰写细节见 SKILL.md 撰写指南。

SKILL.md入口 + 路由
装什么frontmatter（name / description）+ 正文：何时使用 → 快速开始 → 核心流程 → 资源路由表 → Gotchas。只放「每次运行都要用」的内容。
何时读技能被激活时整篇加载进上下文——所以正文只该放每次运行都要用的调度信息，细节外置。
路由表技能命脉。必须写明触发条件，例如「当任务涉及数据库时读 references/database.md」，而不是笼统的「详见 references/」。
## 资源路由表
| 当任务涉及…        | 读取                                  |
|-------------------|---------------------------------------|
| 数据库 / SQL       | references/database.md                |
| 财务口径、科目     | references/finance.md                 |
| 生成报表           | scripts/build-report.py + templates/  |
| API 返回非 200     | references/api-errors.md              |
references/可选

技能的按需知识库。把长篇幅的领域知识、API 细节、边界情况从 SKILL.md 里搬出来——agent 只在路由表命中时才读。撰写细节见 references/ 撰写指南。

REFERENCE.md主技术参考
作用技能最完整的技术说明，是 SKILL.md「简版」的详版兜底。SKILL.md 讲「怎么开始、何时读哪个文件」，REFERENCE.md 讲「每个细节到底是什么」。
内容完整 API 签名与参数表、数据结构定义、可直接运行的完整示例、配置项、边界情况清单。
何时读任务需要精确细节、SKILL.md 的简版说明不够用时。
<domain>.md领域知识
作用把某一垂直领域的专有知识封装成独立文件。技能横跨多个领域（财务 / 法务 / 医疗…）时，一个领域一个文件。
内容该领域特有的术语、口径、规则、约定、合规红线、常见误区。例：finance.md = 会计科目映射 + 财报口径 + 币种/单位约定。
何时读任务明确落在该领域时（如"做一份财报分析" → 读 finance.md）。
为何独立领域知识长且互不相关，合在一起会互相干扰、白占上下文；拆开才能精准按需加载。
api-errors.md条件触发文档
作用把「只在特定条件下才需要」的知识单独成文——平时完全不加载，出问题才读。
内容错误码全表、成因说明、排障步骤、重试/降级策略。
何时读由路由表写明触发条件，例如「当 API 返回非 200 时读取」。
价值就在条件触发——绝大多数正常运行根本用不到，正好省下上下文。
FORMS.md结构化格式
作用规范点名的约定文件名，用于描述表单模板或结构化数据格式。
内容字段清单、字段类型、填写规则、校验规则。
何时读需要填写、解析或校验表单/结构化数据时。
scripts/可选

把确定性、可重复的操作固化成脚本，避免 agent 每次重新「手搓」同样的逻辑。脚本比让模型现写更可靠、更省 token。撰写细节见 scripts/ 撰写指南。

build-report.py业务脚本
作用完成一个具体的确定性任务（此处为生成报表）。当 agent 每次都要重复实现同一段逻辑时，就把它写成脚本。
特征自包含（PEP 723 内联依赖）、非交互、带 --help、结构化输出到 stdout、诊断信息走 stderr。
何时运行路由表命中「需要生成报表」时：uv run scripts/build-report.py。
validate.sh校验脚本
作用充当「验证器」，支撑 validation loop：agent 做完 → 跑校验 → 失败则修复 → 重跑，直到通过。
内容检查产物是否符合规范 / 约束（格式、字段、必填项…）。
要点失败信息必须能自纠——指出期望值 + 可选值，例如 Error: --format must be one of: json, csv, table。
assets/可选

纯静态资源，不含任何逻辑。作用是让 agent 有「具体结构可参照」，比用散文描述更可靠——模型对具体结构 pattern-match 得更好。撰写细节见 assets/ 撰写指南。

templates/输出模板
作用让 agent 按固定结构产出。比用文字描述格式可靠得多。
何时读需要按模板输出时。短模板可直接内联在 SKILL.md，只有长模板或条件模板才放这里。
schemas/数据结构定义
作用定义输入/输出的数据结构，供脚本校验、也供 agent 理解每个字段的含义与约束。
内容JSON Schema、字段定义、类型、必填项、取值范围。
data/查找表
作用存放静态映射数据，供 agent 或脚本查询，避免把大表硬编码进 SKILL.md 或脚本。
内容国家/地区代码、币种、状态码映射、枚举字典、行业分类等。
evals/可选

技能的质量测试。回答「这个技能可靠吗、比没有它强多少」，并给出可迭代的反馈闭环。撰写细节见 evals/ 撰写指南。

evals.json测试用例 + 断言
作用定义测试用例：每条含一句真实提示词、期望结果、以及可验证的断言。
何时读开发/迭代技能时用来跑评测——不参与技能的正常运行。
files/测试输入
作用存放测试用例所依赖的输入文件（样例 CSV、PDF 等）。
要点起步 2–3 条即可；提示词要真实（带路径、口语、错别字），并覆盖边界情况。
agents/可选

存放厂商特定配置——给客户端（harness）读，不是给 agent 读的指令。它不是通用标准：不同客户端认不认、放什么，各不相同，有的客户端根本不看这个目录。

*.yaml厂商配置
作用承载 UI 元数据、依赖声明、调用策略等——这些属于"产品界面"，而不是"技能内容"。
装什么显示名 / 短描述 / 图标 / 品牌色 / 默认提示语；依赖声明；调用策略。
要点只放当前客户端支持的字段；换客户端可能不生效。不要把该给 agent 的指令放这里——agent 不读它。
调用策略显式调用 vs 自动触发
默认技能进入候选池，agent 按 description 自动判断是否加载。
改为显式可配置为不自动加载——技能不进模型上下文，只能由用户显式点名调用。
什么时候用技能带副作用，或你希望"只在明确需要时才用"时。这类策略属于客户端配置，不要靠描述里的措辞去实现。
依赖声明需要外部服务时
作用声明技能需要的外部工具 / 服务（例如某个 MCP 服务），让客户端在加载前知道要先接好。
与正文的分工这里声明"需要什么"，正文的"依赖"一节说明"怎么用"。字段格式因客户端而异。
README / LICENSE / CHANGELOG通常不必加

规范允许技能目录里放任意文件。但除非有明确的打包或分发要求，否则不要默认添加这些——它们对 agent 的行为没有任何影响，只会让目录变乱。

什么时候才加按需
LICENSE要对外分发时才需要；也可只在 frontmatter 的 license 字段里写许可证名。
README只有需要向人类读者交代背景、安装或贡献方式时才加。
CHANGELOG只有需要对外维护版本记录时才加。
一个常见错误陷阱
别把指令写进 READMEagent 根本不读 README。任何"希望 agent 照做"的内容，都必须写进 SKILL.md 或它引用的文件。

交付前自检清单

  • 根目录有 SKILL.md，且 name 与目录名一致
  • 目录名 = 技能名（kebab-case）
  • 每个已存在的目录都有明确用途，不是"以后可能用到"
  • 每个资源文件都能在 SKILL.md 里找到触发条件
  • 引用一律相对路径，且只一层深
  • 没有把给 agent 的指令写进 README
