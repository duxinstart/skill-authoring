完整示例：skill-authoring

跟着一个真实可用的技能，看它如何从最小版逐阶段生长为完整版。每一步都由一个真实的"痛点"触发——而不是一开始就规划好整棵目录树。

关于这个示例：skill-authoring 是一个「帮你写 Agent Skill」的技能——它真实存在于本站目录中（skill-authoring/），可以直接安装使用。它确实有点"元"（一个讲怎么写技能的站点里，放了一个帮你写技能的技能），但正因如此，它天然要用到 references/、scripts/、assets/、evals/ 全部四类目录，是绝佳的贯穿样例。

阶段 1 · 最小版：只写 SKILL.md

起点要尽可能小。先让它能跑通一个真实任务，不预设任何目录。

要解决用户想新建一个技能，但不知道从哪下手。
产出一个 SKILL.md：说清技能做什么、何时用，以及最短的操作步骤。
skill-authoring/
└── SKILL.md

SKILL.md（最小版节选）

---
name: skill-authoring
description: >
  创建、校验与优化 Agent Skill。当用户想新建一个 skill、
  校验或调试已有 skill 时使用。
---

# Skill Authoring

## 何时使用
当用户想新建 / 校验 / 优化一个 Agent Skill 时。

## 核心流程
1. 明确技能做什么、何时触发
2. 创建目录与 SKILL.md
3. 写 frontmatter（name / description 必需）
4. 写正文
5. 校验
这一阶段的关键决策：先不建任何子目录。如果技能只需要几十行就能说清，它就该停在这里——不是所有技能都需要长大。

阶段 2 · 内容变长 → 拆出 references/

真实痛点：用着用着，正文开始塞不下。

触发理由为了讲清 frontmatter 每个字段的约束、命名的坑、校验报错怎么修，正文迅速膨胀。而其中大部分内容只在特定情况下才需要（比如"校验失败时"）。
做法把细节移出去，正文只留主干 + 一张资源路由表。
skill-authoring/
├── SKILL.md
└── references/
    ├── REFERENCE.md            # 格式规范细则（字段、命名、目录约定）
    ├── description-guide.md    # 描述写法与触发优化
    └── validation-errors.md    # 条件触发：校验失败时才读

正文里新增的路由表

## 资源路由表
| 当任务涉及… | 读取 |
|---|---|
| frontmatter 字段、命名、目录约定 | `references/REFERENCE.md` |
| description 怎么写、如何提高触发率 | `references/description-guide.md` |
| 校验报错、不知道错在哪 | `references/validation-errors.md` |
注意：validation-errors.md 是条件触发文档——平时完全不加载，只有校验失败时才读。这正是把内容拆出去的价值：省上下文。

阶段 3 · 逻辑重复 → 加 scripts/

真实痛点：agent 每次都在重写同样的逻辑。

触发理由观察执行轨迹发现：每次新建技能，agent 都要从头拼一遍目录骨架；每次校验，都在临时手写检查脚本。这是"该固化成脚本"的典型信号。
做法把三段重复逻辑写成经过测试的脚本。
skill-authoring/
├── SKILL.md
├── references/  …（不变）
└── scripts/
    ├── scaffold.py           # 生成技能骨架
    ├── validate.py           # 校验技能（优先调用官方 skills-ref）
    └── lint_description.py   # 检查描述长度与触发表述

脚本要点（以 validate.py 为例）

自包含用 PEP 723 内联声明依赖，一条命令即可运行。
可降级优先调用官方 skills-ref；未安装时退化为内置格式检查，并在输出的 engine 字段标明用的是哪套。
结构化输出JSON 走 stdout，诊断走 stderr，便于 agent 解析。
{
  "valid": true,
  "engine": "skills-ref",
  "errors": []
}

阶段 4 · 格式要固定 → 加 assets/

真实痛点：骨架和字段清单需要稳定、可复用。

触发理由骨架模板写在脚本里，改起来麻烦；字段清单反复被引用，却散落在正文各处。
做法把静态资源抽到 assets/，脚本从中读取。
skill-authoring/
├── SKILL.md
├── references/  …（不变）
├── scripts/     …（不变）
└── assets/
    ├── templates/SKILL.md.template        # 骨架模板（scaffold.py 读取它）
    ├── schemas/frontmatter.schema.json    # frontmatter 结构定义
    └── data/field-catalog.json            # 字段速查表
关键点：模板文件名用 SKILL.md.template 而非 SKILL.md——避免它被技能扫描器误认成一个名为 templates 的技能。
脚本真的用了它scaffold.py 会优先读取 assets/templates/SKILL.md.template，读不到才回退到内置模板。这样 assets 不是摆设。

阶段 5 · 要长期维护 → 加 evals/

真实痛点：改动之后，怎么知道没把原来好用的功能改坏？

触发理由技能要持续维护，需要一组用例来锁定质量、防止回退。
做法加测试用例与输入素材。
skill-authoring/
├── SKILL.md
├── references/  …（不变）
├── scripts/     …（不变）
├── assets/      …（不变）
└── evals/
    ├── evals.json
    └── files/
        ├── README.md
        └── my-skill/SKILL.md   # 故意写坏的样例，用于测试校验流程

用例示例

{
  "id": 2,
  "prompt": "我按文档写了个 skill，但 skills-ref validate 一直报错，帮我看看哪里不对？",
  "expected_output": "运行校验、定位具体错误，并给出可执行的修复建议。",
  "files": ["evals/files/my-skill/SKILL.md"],
  "assertions": [
    "实际运行了校验（而非仅凭猜测）",
    "指出的错误与文件中的真实问题一致",
    "给出了具体的修复方式"
  ]
}
一个坑：evals/files/my-skill/SKILL.md 也是嵌套的 SKILL.md，可能被扫描器当成技能。所以素材目录里放了一份 README.md 明确标注"这是测试素材，不是可安装的技能"。

完整版总览

五个阶段长完，它变成了这样——一个真实可用、四类目录齐备的技能。

  • skill-authoring/帮你新建 / 校验 / 优化 Agent Skill
    • SKILL.md必需入口 + 资源路由表（64 行）
    • references/可选按需知识库
      • REFERENCE.md格式规范细则
      • description-guide.md描述写法与触发优化
      • validation-errors.md条件触发：校验失败时读
    • scripts/可选可执行脚本
      • scaffold.py生成技能骨架
      • validate.py校验（包装 skills-ref）
      • lint_description.py检查描述质量
    • assets/可选静态资源
      • templates/SKILL.md.template骨架模板
      • schemas/frontmatter.schema.jsonfrontmatter 结构定义
      • data/field-catalog.json字段速查表
    • evals/可选评测
      • evals.json3 条测试用例 + 断言
      • files/测试素材（含故意写坏的样例）
    • README.md给人看维护者说明

如何验证这个技能真的能用

下面这组命令由你手动执行——它们会证明：格式合规、脚本可跑、示例真实。

① 安装官方校验库（可选，装了 validate.py 会用它）

cd <agentskills>/skills-ref
python3 -m venv .venv && source .venv/bin/activate && pip install -e .

② 校验示例技能本身（预期："valid": true）

python3 skill-authoring/scripts/validate.py skill-authoring

③ 生成一个新技能骨架，再用同一套工具校验它

python3 skill-authoring/scripts/scaffold.py demo-skill --out /tmp
python3 skill-authoring/scripts/validate.py /tmp/demo-skill

④ 检查故意写坏的样例——应当报错（证明校验真的在工作）

python3 skill-authoring/scripts/validate.py skill-authoring/evals/files/my-skill
# 预期：valid = false，并列出 name 大小写/目录名不一致、未定义字段 version 等问题

python3 skill-authoring/scripts/lint_description.py skill-authoring/evals/files/my-skill
# 预期：对过于笼统的 description 给出 warning
判定标准：② 与 ③ 应通过；④ 应失败——第 ④ 步失败恰恰说明校验逻辑有效。
