SKILL.md 撰写指南

它是技能的唯一入口，被激活时整篇载入上下文。本页从零讲清它的每一部分该怎么写——读完你应当能独立写出一个合规、可用的 SKILL.md。

1. 阅读须知

一句话原则：调度信息必须完整、清晰；冗余必须剔除。 这两件事常被混为一谈。「精简」的对象是冗余——agent 早已知道的通用知识、只有特定情况才用到的细节；不是调度所需的必要信息。SKILL.md 是全局调度文档，激活条件、核心流程、资源路由、关键约束都必须写清楚；为了"短"而删掉必要的调度说明，是错误的方向。

官方对篇幅的态度是建议、不是硬性：正文建议 < 5000 tokens / < 500 行（specification.mdx）。同时 best-practices 提醒：技能被激活后正文整篇进入上下文，每个 token 都在与对话历史、其他技能争夺注意力，「过度全面的技能弊大于利」。所以正确做法既不是"越短越好"，也不是"越多越好"，而是——把调度所需的写清楚，把冗余的删掉。

关于本页内容的出处

本页内容分三类来源：官方硬性要求（如 frontmatter 字段约束）、官方建议（如写作原则，来自 best-practices）、以及实践经验归纳（如后文的「建议模板」）。凡属第三类，文中都会明确写出「这是建议、非官方要求」，请勿当作规范。

本页的三种标记

硬性违反会被官方校验器拒绝 建议官方最佳实践，不做不报错但效果差 实验性客户端支持不一，谨慎使用

2. 定位与心智模型

一个比喻：SKILL.md 是「前台接待」

它不亲自干活。它只做两件事：确认来意（这个技能是干什么的、什么时候该用），以及指引去处（遇到不同情况该去读哪个文件）。真正的工作由正文流程、scripts/、references/ 完成。

它什么时候被读

层级加载内容时机与预算
元数据name + description会话启动时加载全部技能——约 50–100 tokens / 个，只够判断相关性。
指令整篇 SKILL.md 正文技能被激活时加载——官方建议 < 5000 tokens / < 500 行（非硬性门槛）。
资源scripts/ references/ assets/正文引用到、且任务需要时才逐个加载。

由此推出两条原则

  • 调度信息必须完整清晰——激活条件、核心流程、资源路由、关键约束，一个都不能省。
  • 偶尔才用的细节外置——并在流程中写明「走到哪一步、读哪份文件」。

3. frontmatter 详解

SKILL.md 必须以 YAML frontmatter 开头（首行 ---），后接 Markdown 正文。字段是一个封闭集合，多一个都会失败。

字段必需性一句话说明
name必需技能标识，必须等于父目录名
description必需决定技能能否被触发
license可选许可证
compatibility可选环境要求
metadata可选自定义键值对
allowed-tools可选预授权工具列表（实验性）

name 硬性

是什么技能的标识符，同时也是它在磁盘上的目录名。
约束1–64 字符；仅小写字母、数字、连字符；不可首尾为连字符；不可含连续连字符 --；必须等于父目录名。
建议用 kebab-case 的动宾短语，如 pdf-processing、code-review。
常见错误① 改名时只改了目录或只改了字段；② 用了大写或下划线；③ 用中文名——校验前会做 NFKC 规范化，非 ASCII 字符不在允许集合内。
# 合法
name: pdf-processing

# 非法
name: PDF-Processing      # 含大写
name: -pdf                # 以连字符开头
name: pdf--processing     # 连续连字符

description 硬性

是什么agent 决定「要不要加载这个技能」的唯一依据。
约束1–1024 字符，非空。
建议同时说清「做什么」与「何时用」，并带上便于检索的关键词。
常见错误只写"做什么"不写"何时用"——技能将永不触发。
# 差
description: 帮助处理 PDF。

# 好
description: >
  提取 PDF 文本与表格、填写表单、合并多个 PDF。
  当用户处理 PDF 文档，或提到 PDF、表单、文档提取时使用本技能，
  即使用户没有明确说"提取"。

描述是触发成败的关键，值得单独深入。完整方法（含触发优化闭环）见 描述与触发优化。

license 硬性

是什么技能适用的许可证。
建议保持简短——写许可证名，或指向随附的许可证文件。
license: Apache-2.0
# 或
license: Proprietary. LICENSE.txt has complete terms

compatibility 硬性

是什么技能的环境要求（目标产品、依赖包、网络等）。
约束若提供，1–500 字符。
建议只在确实有特定环境要求时才写——多数技能不需要这个字段。
compatibility: Requires Python 3.12+ and uv
compatibility: Requires git, docker, jq, and access to the internet

metadata 硬性

是什么string → string 的键值对，用来放规范未定义、但你想保留的信息。
建议键名取得独特一些，避免与其他客户端冲突。
常见错误把 version、author 直接写成顶层字段——那会被判为未定义字段而失败。它们属于 metadata。
metadata:
  author: example-org
  version: "1.0"

allowed-tools 实验性

是什么空格分隔的、预授权可直接运行的工具列表。
注意这是实验性字段，各客户端支持程度不一。不要把它当成硬依赖。
allowed-tools: Bash(git:*) Bash(jq:*) Read
白名单警告：frontmatter 是封闭字段集。出现上表之外的任何字段，官方校验器会直接判失败。需要自定义信息，一律放进 metadata。

4. 正文结构

先看官方口径

官方对正文格式没有强制要求。specification.mdx 原文："There are no format restrictions. Write whatever helps agents perform the task effectively." 官方只推荐了三类内容：分步指令、输入/输出示例、常见边界情况。

换句话说：不存在「必须包含哪几个部分」的官方规定。下面给的是一个建议模板——来自实践经验归纳，非官方要求。请按技能规模与类型增删，不要机械照抄。

建议模板（非官方要求，可增删）

组成部分何时需要说明
激活条件 & 适用边界建议常有确认「找对了技能」，并划清不适用的范围。与 frontmatter 的 description 呼应，但不重复。
核心流程几乎必备主干。资源路由就嵌在流程里——走到某一步、需要读哪份文档，在该步直接写明。
关键规则 / 约束建议常有必须遵守的硬约束、红线，以及反直觉的 Gotchas。
身份设定按需只在需要稳定角色或语气时才有价值（如审阅、写作类技能）。对简单技能是纯 token 浪费——不是必备项。
快速开始按需技能较复杂时，给一条最短的可跑路径。
校验循环按需产出有客观对错标准时，让 agent 自检。
规模决定取舍。一个"掷骰子"技能只需核心流程；一个大型技能才需要把上面几乎全部写齐。不要因为模板列了 6 项就都写上。
特殊技能追加。某些领域需要额外部分：写作类常需追加「协作规范 / 铁律」；数据类常需追加「口径定义」。追加什么，取决于该领域最容易出错的地方。

三处重点，写法示例

激活条件 & 适用边界

作用让 agent 确认「找对了」，并排除不该用的情况。
## 何时使用
当用户提供财务数据（CSV / Excel / 数据库导出）并希望得到分析
结论或成文报告时。**不适用**于：单纯的格式转换、数据录入。

核心流程（含资源路由）

作用技能主干。资源路由直接嵌在每一步里——agent 走到哪一步，就知道该读什么。
写法脆弱、必须严格顺序的步骤写成强制命令；灵活处给原则、解释"为什么"。
## 核心流程
1. 读数据，识别期间与科目
2. 计算核心指标 —— 公式细节见 `references/REFERENCE.md`
3. 按 `assets/templates/report.md` 输出报告
4. 交付前运行 `scripts/validate_report.py`；
   若报错，按 `references/data-errors.md` 排查
也可以另给一张汇总路由表便于总览——但流程里的路由不能省，因为那才是 agent 真正会照着走的地方。

关键规则 / Gotchas

作用往往是整篇价值最高的部分——记录反直觉、环境特有的坑。
写法具体到"不加这条 agent 就会做错"的事实，而非"要妥善处理错误"这类空话。
## Gotchas
- 金额单位可能是元或万元，**务必先确认**，否则指标差 10000 倍。
- 部分数据用软删除，统计前需过滤 `deleted_at IS NULL`。
- 环比需要上期数据；若缺失，**明确说明而非默认填 0**。

5. 写作原则

这些是建议而非硬性要求——但它们决定了技能是"能用"还是"好用"。

A · 内容从哪来

从真实专长出发别只让模型凭通用知识生成——那样得到的是"妥善处理错误"这类空话。要么从一次真实任务里提取（记录成功的步骤、你的纠正、输入输出格式、你补充的背景），要么从项目制品里合成（内部文档、runbook、API 规范、代码评审意见、事故报告）。
用真实执行迭代初稿几乎都要打磨。拿真实任务跑一遍，把结果（不只是失败）反馈回来：什么被误触发？漏了什么？哪些可以砍？读执行轨迹，不只看最终输出——如果 agent 在绕路，通常是指令太含糊、或塞了不适用于当前任务的条目。

B · 写多少

只写 agent 不知道的项目特有约定、领域流程、非显然的边界情况、该用哪个工具。不必解释"PDF 是什么""HTTP 怎么工作"。
适度详细过度全面的技能弊大于利——agent 会难以提取相关部分，甚至被不适用的指令带偏。简洁的分步指引 + 一个可用示例，胜过面面俱到的文档。
设计内聚单元决定技能覆盖什么，就像决定一个函数该做什么：要封装一个连贯的工作单元。太窄会迫使多个技能同时加载；太宽又难以被精确触发。"查询数据库并格式化结果"是一个连贯单元，"外加数据库运维"就过宽了。

C · 怎么写

给默认值，不给菜单多个方案都行时，挑一个默认 + 简短提一句备选，别并列罗列让模型纠结。
讲流程，不讲答案教 agent「如何应对这一类问题」，而非「这次该输出什么」。细节可以具体，但方法要能泛化。
按脆弱性校准任务灵活 → 给自由 + 解释"为什么"；操作脆弱、必须一致 → 写死命令（"严格按此序列，不要改参数"）。同一个技能里，不同部分可以不同力度。

6. 常用内容模式

可复用的结构技巧，按需取用——不是每个技能都需要全部。

Gotchas 清单环境特有的反直觉事实。每次纠正 agent 的错误后，都把纠正补进来——这是最直接的迭代方式。
输出模板要固定格式时给模板（比散文描述可靠）。短模板内联在正文；长模板/条件模板放 assets/ 并在路由表引用。
进度清单多步且有依赖时，用可勾选清单帮 agent 跟踪、防止跳步。
校验循环"做 → 校验 → 修 → 重跑"，用脚本或参考清单当验证器。
先规划后执行批量/破坏性操作：先生成中间计划 → 对照事实源校验 → 通过后才执行。关键是那步"校验"。
何时把逻辑写成脚本若发现 agent 每次都重写同一段逻辑（建图表、解析格式、校验输出），就该把它固化成经过测试的脚本。
## 表单填写（先规划后执行）
1. 提取表单字段 → form_fields.json
2. 生成 field_values.json（字段 → 目标值）
3. 校验：validate_fields.py（检查字段存在、类型兼容、必填不缺）
4. 失败则改 field_values.json 重校
5. 通过后填写 → output.pdf

7. 交付前自检清单

frontmatter

  • name 与目录名完全一致，且全小写、无连续连字符
  • description 同时写了「做什么」与「何时用」，且 ≤1024 字符
  • 没有出现白名单之外的字段（version / author 等应放进 metadata）
  • 有环境要求时，已在 compatibility 中声明

正文

  • 调度信息完整：激活条件、核心流程、关键约束都已写清
  • 资源路由清晰：流程的每一步都指明了需要读哪份文档
  • 冗余已剔除：没有解释 agent 已知的通用知识，没有保留只有特定情况才用的细节
  • 文件引用用相对路径，且只一层深
  • 给的是默认方案，而非并列菜单
  • 脆弱步骤写成了强制指令，灵活步骤给了原则
  • （可选）篇幅：官方建议 < 5000 tokens / < 500 行；明显超出时，优先把细节移入 references/

整体

  • 用真实任务跑过一遍，并据结果做过至少一轮修正
  • 确认技能被正确触发（见 描述与触发优化）

8. 常见错误速查

错误后果 / 纠正
为了"短"而删掉必要的调度信息agent 不知道要做什么、读什么 → 调度信息必须完整；精简的对象是冗余
把偶尔才用的细节塞进正文白占上下文 → 移到 references/，并在流程中写明何时读
只写"详见 references/"agent 不知道何时加载 → 必须写触发条件
解释通用知识（"PDF 是一种文件格式…"）纯浪费上下文 → 删
并列罗列一堆工具/方案模型纠结 → 改成"默认 + 备选"
把给 agent 的指令写进 README.md模型不读它 → 指令必须进 SKILL.md
description 只写"做什么"技能永不触发 → 补上"何时用"
自创 frontmatter 字段校验直接失败 → 放进 metadata
name 与目录名不一致校验失败 → 二者改成一致
技能覆盖范围过大难以被精确触发 → 拆成多个内聚技能
