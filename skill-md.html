SKILL.md 撰写指南

它是技能的唯一入口，被激活时整篇载入上下文。本页从零讲清它的每一部分该怎么写——读完你应当能独立写出一个合规、可用的 SKILL.md。

1. 阅读须知

一句话原则：调度信息必须完整、清晰；冗余必须剔除。 这两件事常被混为一谈。「精简」的对象是冗余——agent 早已知道的通用知识、只有特定情况才用到的细节；不是调度所需的必要信息。SKILL.md 是全局调度文档，激活条件、核心流程、资源路由、关键约束都必须写清楚；为了"短"而删掉必要的调度说明，是错误的方向。

技能被激活后，正文会整篇进入上下文——每个 token 都在与对话历史、其他技能争夺注意力。而且，过度全面的技能弊大于利。所以正确做法既不是"越短越好"，也不是"越多越好"：把调度所需的写清楚；条件性细节尽早外移——不要等到文件臃肿了才动手。

关于本页内容的出处

本页内容分三级：硬性（运行时强制，违反会导致技能无法被加载）、建议（我们给出的推荐，不做不会出错但效果会差）、实验性（客户端支持不一）。文中逐条标明，请勿混淆。

本页的三种标记

硬性运行时强制，违反会导致技能无法被加载 建议我们给出的推荐，不做不报错但效果差 实验性客户端支持不一，谨慎使用

2. 定位与心智模型

它承担两件事

SKILL.md 既装载主干流程（agent 照着它一步步做），又负责调度（把"偶尔才用的细节"指向 references/、scripts/、assets/）。它不是"只做路由、不干活"——主干流程就在正文里；被外置的只是细节。

它什么时候被读

层级加载内容时机与预算
元数据name + description会话启动时加载全部技能——约 50–100 tokens / 个，只够判断相关性。
指令整篇 SKILL.md 正文技能被激活时加载整篇——正文的每一句都在消耗上下文。
资源scripts/ references/ assets/正文引用到、且任务需要时才逐个加载。

由此推出两条原则

  • 调度信息必须完整清晰——激活条件、核心流程、资源路由、关键约束，一个都不能省。
  • 偶尔才用的细节外置——并在流程中写明「走到哪一步、读哪份文件」。

3. 从零到成稿：六步流程

拿到一个任务，按这个顺序走就能写出第一版 SKILL.md。每步都指向后面的细节。

定边界

写一句话：这个技能替用户完成什么？何时用？何时不用？边界说不清就先别动笔——见第 6 节「设计内聚单元」。

起 frontmatter

先写 name（= 目录名，kebab-case）和 description（做什么 + 何时用）。字段细节见第 4 节；描述怎么写另见 描述与触发优化。

写主干流程

编号列出「做这件事的步骤」，每步一句话。见第 5 节。

嵌资源路由

走到哪一步需要读哪份文档，就在那一步写明。见第 5 节。

补关键约束

把「不加这条 agent 就会做错」的事实写成 Gotchas。见第 5 节。

自检 + 迭代

对照第 8 节的清单检查；再用真实任务跑一遍，据结果修正。触发问题见 描述与触发优化。

起步提示：先只写 SKILL.md 就够了。只有当某类内容多到撑不住正文、或某段逻辑反复被重写时，才按需增加 references/、scripts/、assets/、evals/。目录取舍详见 设计流程。

4. frontmatter 详解

SKILL.md 必须以 YAML frontmatter 开头（首行 ---），后接 Markdown 正文。字段是一个封闭集合，多一个都会失败。

字段必需性一句话说明
name必需技能标识，必须等于父目录名
description必需决定技能能否被触发
license可选许可证
compatibility可选环境要求
metadata可选自定义键值对
allowed-tools可选预授权工具列表（实验性）

表中「必需性」指字段是否必须出现；字段小标题上的标记指其约束的强度（硬性 = 违反会被校验器拒绝）。两者是不同维度，别混为一谈。

name 硬性

是什么技能的标识符，同时也是它在磁盘上的目录名。
约束1–64 字符；仅小写字母、数字、连字符；不可首尾为连字符；不可含连续连字符 --；必须等于父目录名。
建议用 kebab-case 的动宾短语，如 pdf-processing、code-review。
常见错误① 改名时只改了目录或只改了字段；② 用了大写、下划线或空格。
关于非 ASCII 名校验器支持 i18n 的 Unicode 字母（字符判定 isalnum() 对中文返回 True），所以中文名不会被拒绝。但仍建议用 ASCII——目录名要一致、跨平台可移植性更好。 建议
# 合法
name: pdf-processing

# 非法
name: PDF-Processing      # 含大写
name: -pdf                # 以连字符开头
name: pdf--processing     # 连续连字符

description 硬性

是什么agent 决定「要不要加载这个技能」的主要依据——它是判断是否触发的首要机制。
约束1–1024 字符，非空。
建议同时说清「做什么」与「何时用」，并带上便于检索的关键词。
常见错误只写"做什么"不写"何时用"——技能很可能不会被触发。
# 差
description: 帮助处理 PDF。

# 好
description: >
  提取 PDF 文本与表格、填写表单、合并多个 PDF。
  当用户处理 PDF 文档，或提到 PDF、表单、文档提取时使用本技能，
  即使用户没有明确说"提取"。

描述是触发成败的关键，值得单独深入。完整方法（含触发优化闭环）见 描述与触发优化。

license 可选 · 无硬性约束

是什么技能适用的许可证。
建议保持简短——写许可证名，或指向随附的许可证文件。
license: Apache-2.0
# 或
license: Proprietary. LICENSE.txt has complete terms

compatibility 硬性

是什么技能的环境要求（目标产品、依赖包、网络等）。
约束若提供，1–500 字符。
建议只在确实有特定环境要求时才写——多数技能不需要这个字段。
compatibility: Requires Python 3.12+ and uv
compatibility: Requires git, docker, jq, and access to the internet

metadata 可选 · 无硬性约束

是什么string → string 的键值对，用来放规范未定义、但你想保留的信息。
建议键名取得独特一些，避免与其他客户端冲突。
常见错误把 version、author 直接写成顶层字段——那会被判为未定义字段而失败。它们属于 metadata。
metadata:
  author: example-org
  version: "1.0"

allowed-tools 实验性

是什么空格分隔的、预授权可直接运行的工具列表。
注意这是实验性字段，各客户端支持程度不一。不要把它当成硬依赖。
allowed-tools: Bash(git:*) Bash(jq:*) Read
白名单警告：frontmatter 是封闭字段集。出现上表之外的任何字段，校验器会直接判失败。需要自定义信息，一律放进 metadata。

5. 正文结构

正文决定 agent 具体**怎么做**这件事。下面是我们推荐的正文结构——按这个顺序写，新手也能写出条理清晰的 SKILL.md。

正文没有强制的格式约束（强约束只存在于 frontmatter）。但"不强制"不等于"随便写"——下面这套结构是我们推荐的骨架，按它写能让 agent 更快进入状态。

推荐结构一览

#部分必要性作用
1标题推荐技能名，与目录名一致
2这个技能做什么推荐一两句说明用途
3何时使用 / 何时不用推荐划清边界，避免误用
4核心流程必须分步指令；每步需要的资源就地指明
5关键约束与坑推荐必须遵守的硬规则 + 反直觉的事实
6按需追加按需依赖 / 输出格式 / 校验 / 快速开始
这是骨架，不是清单。第 1–5 项构成一份可用的技能；第 6 项视任务追加。不要为了凑齐而写没有用的话。

逐项怎么写

① 标题

写什么技能名，用 # 一级标题。
要点与目录名、frontmatter 的 name 保持一致。

② 这个技能做什么

写什么一两句话，说明它替用户完成什么。
要点不要复述 description——那里是给"要不要触发"用的，这里是给"已经开始做"用的。

③ 何时使用 / 何时不用

写什么适用场景 + 明确排除的情况。
要点只在"边界容易搞混"时才值得单列；否则会与 description 重复。
## 何时使用
当用户提供财务数据（CSV / Excel / 数据库导出）并希望得到分析
结论或成文报告时。**不适用**于：单纯的格式转换、数据录入。

④ 核心流程（必写）

写什么分步指令。每步一句话说清"做什么"。
要点资源路由就嵌在每一步里——走到哪一步需要读哪份文档，就在那一步写明。
脆弱、必须严格顺序的步骤写成强制命令；灵活处给原则、解释"为什么"。
## 核心流程
1. 读数据，识别期间与科目
2. 计算核心指标 —— 公式细节见 `references/REFERENCE.md`
3. 按 `assets/templates/report.md` 输出报告
4. 交付前运行 `scripts/validate_report.py`；
   若报错，按 `references/data-errors.md` 排查
也可以另给一张汇总路由表便于总览——但流程里的路由不能省，因为那才是 agent 真正会照着走的地方。

⑤ 关键约束与坑

写什么两类：必须遵守的硬规则；反直觉、环境特有的事实。
要点后者往往价值最高——具体到"不加这条 agent 就会做错"，而非"要妥善处理错误"这类空话。
## Gotchas
- 金额单位可能是元或万元，**务必先确认**，否则指标差 10000 倍。
- 部分数据用软删除，统计前需过滤 `deleted_at IS NULL`。
- 环比需要上期数据；若缺失，**明确说明而非默认填 0**。

⑥ 按需追加

部分什么时候加
依赖技能需要额外的包 / 工具才能跑
输出格式要求固定输出结构时，给模板或格式说明
校验产出有客观对错标准，想让 agent 自检
快速开始技能步骤多，需要一条最短可跑路径
领域特有的部分，自己加。写作类技能可能加「协作规范」，数据类可能加「口径定义」——加什么，取决于你这个领域最容易出错的地方。

6. 写作原则

这些是建议而非硬性要求——但它们决定了技能是"能用"还是"好用"。每条给出「怎么做 + 反例」，可直接照做。

A · 内容从哪来

从真实专长出发别只让模型凭通用知识生成——那样得到的是"妥善处理错误"这类空话。
怎么做先真的用 agent 做一遍这个任务，边做边记四件事：哪些步骤成功了、你在哪里纠正了它、输入输出长什么样、你补充了哪些它原本不知道的背景。再把这份记录整理成技能。
已有现成材料时（内部文档、runbook、API 规范、评审意见、事故报告），把材料交给模型去合成，而不是让它凭空写。
用真实执行迭代初稿几乎都要打磨。
怎么做写完立刻拿 2–3 个真实任务跑一遍，然后读执行轨迹（不只是最终输出），记录三件事：什么被误触发、漏了什么、哪句指令没起作用。把这三件事交给模型让它改，再跑一遍。
更严格的做法用一个干净的独立会话来测：只给它真实请求 + 技能本身 + 最少量的输入文件，不要告诉它你期望的答案、你怀疑的问题、或你打算怎么改。否则测出来的只是"它能不能照着答案复述"，而不是"这个技能本身管不管用"。
隔离产物把测试产生的东西写到临时目录，别混进工作区——否则会污染后续测试。
反例只改措辞、不看轨迹——等于盲改。

B · 写多少

只写 agent 不知道的项目特有约定、领域流程、非显然的边界情况、该用哪个工具。
怎么做逐句自问「不给它，agent 会做错吗？」答案是"不会"就删。
反例花一段话解释"PDF 是什么""HTTP 怎么工作"。
适度详细过度全面的技能弊大于利——agent 会难以提取相关部分，甚至被不适用的指令带偏。
怎么做写完数一数：如果覆盖了大量"可能用不上"的边界情况，先删掉，等真的出错再加回来。
设计内聚单元技能要封装一个连贯的工作单元。
怎么做用一句话描述技能边界；如果这句话里出现"并且"连接的两个不相干任务，就该拆。
反例把"查询数据库并出报表"和"数据库运维"塞进同一个技能。

C · 怎么写

给默认值，不给菜单多个方案都行时，别并列罗列让模型纠结。
怎么做选一个写进正文，备选只用一句话带过（"扫描件再用 pdf2image"）。
反例"可以用 pypdf、pdfplumber、PyMuPDF 或 pdf2image……"
讲流程，不讲答案教 agent「如何应对这一类问题」，而非「这次该输出什么」。
怎么做把"这次要输出什么"改写成"遇到这类任务按什么步骤做"。
反例写死一条具体 SQL，而不是"先读 schema → 按外键 join → 应用筛选 → 聚合"。
按脆弱性校准同一个技能里，不同步骤可以用不同力度。
怎么做给每个步骤标一下：做错了会不会出问题？会 → 写成强制命令（"严格按此序列，不要改参数"）；不会 → 给原则 + 解释"为什么"。
反例把灵活的探索性步骤写成死命令；或把不可逆的迁移步骤写成"灵活处理"。

7. 常用内容模式

可复用的结构技巧，按需取用——不是每个技能都需要全部。每个模式给出「什么时候用 → 怎么写」。

Gotchas 清单什么时候用：发现了反直觉、环境特有的坑。
怎么写每条写成「事实 + 后果」——"金额单位可能是元或万元，不确认会让指标差 10000 倍"。
维护：每次纠正 agent 的错误后，把纠正补进这一节。
输出模板什么时候用：需要固定输出结构。
怎么写短模板直接内联在正文；长模板、或只在特定情况用的模板放 assets/，并在路由里写明何时读。
进度清单什么时候用：步骤多且有依赖，怕 agent 跳步。
怎么写用可勾选列表，每步一行 - [ ] 步骤，必要时附上该步要跑的脚本。
校验循环什么时候用：产出有客观对错标准。
怎么写写明"做 → 跑校验 → 失败则修复 → 重跑"，并指明验证器是谁（脚本 / 参考清单 / 自检项）。
先规划后执行什么时候用：批量或破坏性操作。
怎么写分四步：生成中间计划 → 对照事实源校验 → 失败则改 → 通过才执行。关键是那步"校验"。
何时把逻辑写成脚本怎么判断：读几次执行轨迹，如果 agent 每次都重写同一段逻辑（建图表、解析格式、校验输出），就把它固化成 scripts/ 下的脚本。
## 表单填写（先规划后执行）
1. 提取表单字段 → form_fields.json
2. 生成 field_values.json（字段 → 目标值）
3. 校验：validate_fields.py（检查字段存在、类型兼容、必填不缺）
4. 失败则改 field_values.json 重校
5. 通过后填写 → output.pdf

8. 交付前自检清单

frontmatter

  • name 与目录名完全一致，且全小写、无连续连字符
  • description 同时写了「做什么」与「何时用」，且 ≤1024 字符
  • 没有出现白名单之外的字段（version / author 等应放进 metadata）
  • 有环境要求时，已在 compatibility 中声明

正文

  • 调度信息完整：激活条件、核心流程、关键约束都已写清
  • 资源路由清晰：流程的每一步都指明了需要读哪份文档
  • 冗余已剔除：没有解释 agent 已知的通用知识，没有保留只有特定情况才用的细节
  • 文件引用用相对路径，且只一层深
  • 给的是默认方案，而非并列菜单
  • 脆弱步骤写成了强制指令，灵活步骤给了原则
  • 篇幅自查：正文里是否还留着"偶尔才用"的细节？有就移入 references/

整体

  • 用真实任务跑过一遍，并据结果做过至少一轮修正
  • 确认技能被正确触发（见 描述与触发优化）

9. 常见错误速查

错误后果 / 纠正
为了"短"而删掉必要的调度信息agent 不知道要做什么、读什么 → 调度信息必须完整；精简的对象是冗余
把偶尔才用的细节塞进正文白占上下文 → 移到 references/，并在流程中写明何时读
只写"详见 references/"agent 不知道何时加载 → 必须写触发条件
解释通用知识（"PDF 是一种文件格式…"）纯浪费上下文 → 删
并列罗列一堆工具/方案模型纠结 → 改成"默认 + 备选"
把给 agent 的指令写进 README.md模型不读它 → 指令必须进 SKILL.md
description 只写"做什么"技能很可能不被触发 → 补上"何时用"
自创 frontmatter 字段校验直接失败 → 放进 metadata
name 与目录名不一致校验失败 → 二者改成一致
技能覆盖范围过大难以被精确触发 → 拆成多个内聚技能
