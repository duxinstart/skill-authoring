# description 撰写与触发优化

`description` 是 agent 决定「要不要加载这个技能」的**唯一依据**。写得窄，该触发时不触发；写得宽，不该触发时乱触发。

## 1. 触发是怎么发生的

- 会话启动时，agent 只读到每个技能的 `name` + `description`（约 50–100 tokens）。
- 当用户任务与该描述匹配，agent 才把整篇 `SKILL.md` 读进上下文。
- 因此**描述独自承担了全部触发责任**。

一个前提：agent 通常只对「超出自身能力」的任务才去查技能。像"读这个 PDF"这种一步就能做的事，即便描述完全匹配也可能不触发。所以描述要覆盖**确实需要专门知识**的场景。

## 2. 五条写作原则

1. **用祈使句**。写成给 agent 的指令——"当用户……时使用本技能"，而不是"本技能可以……"。
2. **写用户意图，不写内部实现**。匹配的是用户的话，不是你的实现细节。
3. **宁可"主动"一点**。显式列出适用场景，包括用户没直接点名的情况（"即使用户没有明确提到 X"）。
4. **带上可检索关键词**。领域术语、同义词、常见口语说法。
5. **保持简短**。几句话到一小段；硬上限 1024 字符。

## 3. 好 / 差对照

```yaml
# 差 —— 太笼统，不知道何时用
description: 帮助处理 PDF。

# 差 —— 只说了做什么，没说何时用
description: 一个提取 PDF 文本的工具。

# 好 —— 做什么 + 何时用 + 关键词 + 主动覆盖
description: >
  提取 PDF 文本与表格、填写 PDF 表单、合并多个 PDF。
  当用户处理 PDF 文档，或提到 PDF、表单、文档提取时使用本技能，
  即使用户没有明确说"提取"。
```

## 4. 触发优化闭环

要系统性地提高触发准确率，用一组「应触发 / 不应触发」的测试查询来迭代。

### 4.1 设计查询集

约 20 条：8–10 条应触发，8–10 条不应触发。

```json
[
  { "query": "我有个 ~/data/q4.xlsx，C 列是营收、D 列是成本，帮我加一列利润率", "should_trigger": true },
  { "query": "把 json 转成 yaml 最快的方法是什么", "should_trigger": false }
]
```

**应触发的查询**要多变：措辞（正式 / 口语 / 带错别字）、明示程度（直接点名领域 vs 只描述需求）、详略（一句话 vs 带路径和背景）、复杂度（单步 vs 多步）。

**不应触发的查询**里，最有价值的是**近似项（near-miss）**——共享关键词但实际需要别的东西。例如对"CSV 分析"技能：

- 弱负例：`"写个斐波那契函数"`（毫无重叠，测不出东西）
- 强负例：`"帮我改一下 Excel 预算表里的公式"`（共享"表格"概念，但要的是 Excel 编辑，不是 CSV 分析）

### 4.2 计算触发率

同一查询跑多次（建议 3 次），算出**触发率** = 被调用次数 / 总次数。模型行为有随机性，单次不可靠。

- 应触发的查询：触发率 **> 0.5** 算通过
- 不应触发的查询：触发率 **< 0.5** 算通过

### 4.3 训练 / 验证切分

防止过拟合：把查询集切开。

- **训练集（约 60%）**：用来发现问题、指导修改
- **验证集（约 40%）**：只在最后检验改动是否泛化

两组都要含应触发与不应触发的合理比例。切分固定，别每次重洗。

### 4.4 迭代

1. 在训练集与验证集上**评估**当前描述
2. 只在**训练集**上找失败项，指导修改
3. **修改描述**，聚焦泛化：
   - 应触发却失败 → 描述太窄，扩大范围或补充"何时有用"
   - 不应触发却误触 → 描述太宽，补上"不做什么"或划清与相邻能力的边界
   - **不要**把失败查询里的具体词照抄进去——那是过拟合；要提炼出它代表的**一般类别**
4. 重复，直到训练集全通过或不再有显著改善
5. 按**验证集通过率**选出最佳版本——最好的往往不是最后一版

一般 5 轮就够。若一直不改善，问题可能出在查询集本身。

## 5. 应用结果

1. 更新 `SKILL.md` 的 `description`
2. 确认不超过 1024 字符
3. 用几条**全新**查询做一次独立检验（从未参与优化的），确认能泛化
