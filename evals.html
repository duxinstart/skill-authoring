evals/ 撰写指南

技能的质量测试。回答"这个技能可靠吗、比没有它强多少"，并给出可迭代的反馈闭环。

本页内容均为建议。

1. 什么时候需要

  • 技能要长期维护，希望每次改动都能验证不回退。
  • 想量化"有技能 vs 没技能"的效果差异。
  • 想系统性地发现技能的盲区与歧义。
起步建议：先写 2–3 条测试用例，别在没看到第一轮结果前过度投入。用例集可以之后扩充。

2. 从零到成稿：七步流程

建一套评测，按这个顺序做。

写 2–3 条真实用例

用真实用户会打出来的话（带路径、口语）。别一上来就铺满。

准备输入文件

用例依赖的素材放 evals/files/。

跑第一轮

每条用例带技能 / 不带技能各跑一次，形成对照；用干净上下文。

据结果补断言

看到输出之后才知道"成功长什么样"——这时再写可客观验证的断言。

判分与聚合

逐条断言给 PASS / FAIL + 证据；再算 with / without 的通过率、耗时、token。

人工评审

断言只覆盖你想到的点。逐条看真实输出，记录具体反馈。

迭代

把失败断言 + 人工反馈 + 执行轨迹交给模型提改进，再在新的 iteration-N+1/ 重跑。

3. evals.json 结构

放在 evals/evals.json，测试输入文件放 evals/files/。

{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "I have a CSV in data/sales_2025.csv — find the top 3 months by revenue and make a bar chart?",
      "expected_output": "A bar chart of the top 3 months by revenue, with labeled axes.",
      "files": ["evals/files/sales_2025.csv"],
      "assertions": [
        "输出包含柱状图文件",
        "图表恰好显示 3 个月份",
        "两个坐标轴都有标签"
      ]
    }
  ]
}
字段含义与写法
skill_name被测技能名，与技能目录一致。
id用例编号，唯一。
prompt真实用户消息——像用户真会打出来的那样（带路径、口语、错别字）。
expected_output对人类可读的"成功长什么样"的描述。
files用例依赖的输入文件（可选）。
assertions可验证的断言列表——先看到第一轮输出后再补。

4. 用例设计要点

  • 从 2–3 条起步，别一开始就铺满。
  • 变化措辞：有的正式、有的随意（"hey can you clean up this csv"）、有的精确（"Parse the CSV at data/input.csv, drop rows where column B is null"）。
  • 覆盖边界：至少一条测异常输入、罕见请求，或技能指令可能含糊的情形。
  • 用真实上下文：文件路径、列名、个人背景（"我老板让我……"）。"处理一下数据"这种太含糊，测不出东西。

5. 断言怎么写

好的断言

  • "输出文件是合法 JSON"——可程序化验证。
  • "柱状图恰好显示 3 个月份"——具体、可计数。
  • "报告至少包含 3 条建议"——可数。

弱的断言

  • "输出质量好"——太笼统，无法判分。
  • "必须包含 'Total Revenue: $X' 字样"——太脆弱，措辞不同的正确输出会误判失败。
不是所有东西都要断言。写作风格、视觉设计、"感觉对不对"这类难以拆成通过/失败的质量，留给人工评审。断言只用于可客观检查的东西。

6. 怎么运行

核心模式：每条用例跑两次——一次带技能，一次不带（或对上一版本），以形成对照。

工作区结果放在技能目录旁的 workspace，每轮迭代一个 iteration-N/；每条用例下有 with_skill/ 与 without_skill/，各自含 outputs/、timing.json、grading.json。
csv-analyzer/
├── SKILL.md
└── evals/evals.json

csv-analyzer-workspace/
└── iteration-1/
    ├── eval-top-months-chart/
    │   ├── with_skill/    → outputs/ timing.json grading.json
    │   └── without_skill/ → outputs/ timing.json grading.json
    └── benchmark.json     # 聚合统计
隔离每次运行都要干净上下文（子代理或独立会话），确保 agent 只遵循 SKILL.md。
计时记录 token 数与耗时，才能权衡"技能提升质量 vs 增加成本"。

7. 判分与迭代

判分逐条断言给 PASS / FAIL + 具体证据（引用输出，而非主观意见）。可代码检查的（合法 JSON、行数、文件存在）用脚本，更可靠。
聚合算出 with / without 的通过率、耗时、token，并看 delta——技能多花了多少、买回了多少。
人工评审断言只覆盖你想到的点。逐条看真实输出，记录具体反馈（"图表缺轴标签"可执行，"看起来不好"不可执行）。
迭代把失败断言 + 人工反馈 + 执行轨迹交给模型，请它提改进；然后在新 iteration-N+1/ 重跑。
模式识别：总是通过的断言没价值（删掉）；总是失败的断言可能坏了；有技能通过、没技能失败的断言，才是技能真正创造价值的地方。

8. 交付前自检清单

  • 起步 2–3 条用例，提示词真实（带路径、口语、错别字）
  • 至少一条边界用例（异常输入 / 罕见请求 / 指令含糊处）
  • 断言可客观验证——不是"输出质量好"这类无法判分的表述
  • 每条用例带技能 / 不带技能各跑一次，形成对照
  • 每次运行使用干净上下文（独立会话或子代理）
  • 记录了 token 数与耗时，能权衡"提升质量 vs 增加成本"
  • 保留了人工评审环节——断言覆盖不到的质量靠它
  • 改动后在新的 iteration-N+1/ 重跑

9. 常见错误速查

错误后果 / 纠正
提示词太含糊（"处理一下数据"）测不出东西 → 用真实上下文（路径、列名、背景）
断言不可验证（"输出质量好"）无法判分 → 改成可客观检查的表述
断言太脆弱（要求特定措辞）正确输出被误判失败 → 只查实质，不查字面
用同一个会话连跑多条用例上下文互相污染 → 每次用干净会话
只看通过率，不看成本忽略 token / 耗时 → 记录 delta
只靠断言，不做人工评审漏掉断言覆盖不到的质量问题
拿全部查询反复调过拟合 → 留出验证集选版本
