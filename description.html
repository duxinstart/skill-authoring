Triggering

描述与触发优化

description 是 agent 决定「要不要加载这个技能」的唯一依据。写得窄，该触发时不触发；写得宽，不该触发时乱触发。本页讲清怎么写、以及如何系统性地把触发率调上去。

硬性运行时强制，违反会导致技能无法被加载 建议我们给出的推荐，不做不报错但效果差

1. 为什么 description 决定一切

回顾渐进式加载：会话启动时，agent 只读到每个技能的 name + description（约 50–100 tokens / 个）。只有当用户任务与描述匹配，agent 才会把整篇 SKILL.md 读进上下文。

结论：描述独自承担了全部触发责任。如果描述没有传达出"何时有用"，agent 就不知道要去找它——技能写得再好也没用。

一个容易忽略的前提

agent 通常只对超出自身能力的任务才去查技能。像"读这个 PDF"这种一步就能做的事，即便描述完全匹配，也可能不触发——因为 agent 用基础工具就能完成。真正需要专门知识的场景（不熟悉的 API、领域流程、罕见格式），才是描述发挥作用的地方。

硬性约束

长度硬性1–1024 字符，非空。描述在优化过程中容易越写越长，记得回头检查。

2. 五条写作原则

  • 用祈使句建议
    写成给 agent 的指令——"当用户……时使用本技能"，而不是"本技能可以……"。agent 是在决定"要不要行动"。
  • 写用户意图，不写内部实现
    匹配的是用户的话，不是你的实现细节。写"用户想达成什么"，而不是"技能内部怎么算"。
  • 宁可"主动"一点
    显式列出适用场景，包括用户没直接点名的情况——"即使用户没有明确提到 CSV 或分析"。
  • 带上可检索关键词
    领域术语、同义词、常见口语说法，都写进去。
  • 保持简短
    几句话到一小段——够覆盖范围，又不至于在多个技能间撑爆上下文。

3. 好 / 差对照

# 差 —— 太笼统，不知道何时用
description: 帮助处理 PDF。

# 差 —— 只说了做什么，没说何时用
description: 一个提取 PDF 文本的工具。

# 差 —— 罗列实现细节，用户不会这么说
description: 调用 pdfplumber 解析页面对象并遍历提取文本。

# 好 —— 做什么 + 何时用 + 关键词 + 主动覆盖
description: >
  提取 PDF 文本与表格、填写 PDF 表单、合并多个 PDF。
  当用户处理 PDF 文档，或提到 PDF、表单、文档提取时使用本技能，
  即使用户没有明确说"提取"。
对照着看：好的版本既更具体地说了做什么（提取/填表/合并），又更宽地覆盖了何时用（PDF、表单、文档提取；即便没点名关键词）。

4. 触发优化闭环

当技能该触发却不触发、或不该触发却乱触发时，用这套方法来系统性地调，而不是凭感觉改词。

4.1 设计一组测试查询

约 20 条：8–10 条应触发，8–10 条不应触发。存成 JSON。

[
  { "query": "我有个 ~/data/q4.xlsx，C 列是营收、D 列是成本，帮我加一列利润率", "should_trigger": true },
  { "query": "把 json 转成 yaml 最快的方法是什么", "should_trigger": false }
]

应触发的查询：多变化

  • 措辞：有的正式、有的随意、有的带错别字或缩写。
  • 明示程度：有的直接点名领域（"分析这个 CSV"），有的只描述需求（"老板要我从这个数据文件出张图"）。
  • 详略：一句话的短提示，与带路径、列名、背景的长提示都要有。
  • 复杂度：单步任务与多步工作流都要覆盖。
最有价值的应触发查询，是那些"技能确实有用、但光看查询不明显"的——因为那正是描述措辞能起决定作用的地方。

不应触发的查询：找"近似项"

最有用的是 near-miss——共享关键词或概念、但实际需要别的东西的查询。以"CSV 分析"技能为例：

弱负例（测不出东西）强负例（有价值）
"写个斐波那契函数"
毫不相关		 "帮我改一下 Excel 预算表里的公式"
共享"表格"概念，但要的是 Excel 编辑，不是 CSV 分析
"今天天气怎么样？"
无关键词重叠		 "写个 python 脚本把 csv 每行上传到 postgres"
涉及 CSV，但任务是数据库 ETL，不是分析

让查询更真实

真实用户会带上：文件路径（~/Downloads/report_final_v2.xlsx）、个人背景（"我经理让我……"）、具体细节（列名、公司名、数值）、口语与错别字。

4.2 计算触发率

模型行为有随机性——同一查询可能这次触发、下次不触发。所以每条查询要跑多次（建议 3 次），算出触发率＝被调用次数 / 总次数。

查询类型判定
应触发（should_trigger = true）触发率 > 0.5 算通过
不应触发（should_trigger = false）触发率 < 0.5 算通过
怎么判断"触发了没"？看 agent 是否加载了你的 SKILL.md。多数客户端提供执行日志、工具调用记录或 verbose 输出，可据此判断。

4.3 切分训练集 / 验证集

如果拿全部查询来调描述，会过拟合——调出一版只对这批措辞有效、换个说法就失效的描述。

训练集约 60%。用来发现问题、指导修改。
验证集约 40%。先放一边，只在最后检验改动是否泛化。
两组都要含应触发与不应触发的合理比例，别把正例全塞进一组。切分固定，别每次重洗。

4.4 迭代循环

评估

在训练集和验证集上都跑一遍。训练集结果指导改动；验证集结果告诉你改动是否泛化。

只在训练集上找失败项

哪些应触发的没触发？哪些不应触发的触发了？只用训练集的失败来指导修改，把验证集结果排除在决策之外。

修改描述，聚焦泛化

· 应触发却失败 → 描述太窄，扩大范围或补充"何时有用"。
· 不应触发却误触 → 描述太宽，补上"不做什么"或划清与相邻能力的边界。
· 不要把失败查询里的具体词照抄进去——那是过拟合；要提炼出它代表的一般类别。
· 若几轮都卡住，换一个结构性不同的写法（换框架、换句式），而非继续微调。
· 别忘了检查是否还在 1024 字符以内。

重复

直到训练集全部通过，或不再有明显改善。一般 5 轮就够。

按验证集选出最佳版本

以验证集通过率为准。注意：最佳版本往往不是最后一版——后面几版可能已经过拟合训练集了。

如果一直不改善，问题可能出在查询集本身（太简单、太难，或标注错了），而不是描述。

5. 应用与最终验证

更新

把选中的版本写回 SKILL.md 的 description 字段。

确认长度

确认不超过 1024 字符。

独立检验

再写 5–10 条全新查询（应触发与不应触发混合），跑一遍——它们从未参与优化，能给出诚实的泛化检验。

6. 描述自检清单

  • 同时写了「做什么」与「何时用」
  • 用了祈使句（"当……时使用本技能"），而非陈述句
  • 写的是用户意图，不是内部实现细节
  • 显式覆盖了用户没直接点名的场景
  • 含有便于检索的关键词 / 同义词
  • 长度 ≤ 1024 字符，且不至于短到缺乏上下文
  • 用真实查询跑过，确认该触发的会触发、不该触发的不会

7. 常见错误速查

错误后果 / 纠正
只写"做什么"，不写"何时用"很可能不被触发 → 补上适用场景
罗列实现细节（"调用 pdfplumber 解析…"）用户不会这么说 → 改写成用户意图
太笼统（"帮助处理 PDF"）无法匹配具体任务 → 写清具体能力
写得过长撑上下文 → 精简；硬上限 1024 字符
拿全部查询反复调过拟合 → 留验证集，按验证集选版本
把失败查询里的词照抄进去过拟合 → 提炼它代表的一般类别
把"不做什么"全列上描述臃肿 → 只在能防住近似误触发时才加排除
